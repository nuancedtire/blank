## Senior Dev Code Review: This Plan Has Serious Problems

Let me be direct. I've seen this exact pattern of "smart" duplicate detection fail in production multiple times. Each time it was the same story: over-engineered AI solution, under-tested edge cases, and a production incident.

## The Implementation is Fundamentally Flawed

### 1. SHA256 Hash Storage Location is Wrong

You're putting `sha256Hash` in `uploadedDocuments`. That's the **wrong table**.

**Why this is wrong:**
- `uploadedDocuments` is a processing queue table - documents move through states (pending to indexing to indexed)
- What happens when you delete the uploaded document but keep the guideline? **You lose the hash.**
- What if the same content is uploaded twice with different filenames? You'd have two `uploadedDocuments` entries with the same hash but only one `guideline`.

**Correct approach:** Store the hash in the `guidelines` table where the canonical content lives. Or better, a separate `contentHashes` table that maps hash to active guideline ID.

---

### 2. The "Semantic Search for Version Detection" is Reckless

You're proposing to use RAG vector search to find "similar" documents and then use an LLM to compare them. This is **dangerous** for clinical guidelines.

**What could go wrong:**

| Scenario | What Happens | Consequence |
|----------|--------------|-------------|
| Two guidelines about sepsis from different sources | RAG finds them as "similar" | LLM incorrectly flags one as duplicate |
| Updated guideline with major clinical changes | RAG similarity is high | LLM might say "same document, minor changes" |
| Guideline renamed/restructured | RAG similarity is low | Version detection **fails completely** |
| Document with embedded dates | LLM extracts wrong date | Wrong version marked as "newer" |

**The fundamental problem:** You're using **similarity** as a proxy for **version relationship**. These are completely different concepts.

- Similarity = "documents discuss the same topic"
- Version = "document B is a revision of document A"

RAG cannot distinguish between "Sepsis guideline v2.0" and "Sepsis guideline from different hospital." An LLM guessing at it is **not reliable enough for clinical systems**.

---

### 3. The Archive/Restore Flow Has No Transactional Safety

Look at your proposed archive flow:

1. Set status = "archived"
2. Remove RAG embeddings
3. Update version history

**What happens when step 2 fails?**
- DB says archived, RAG still returns it in search
- Users see document in search that they can't access
- **Data inconsistency** that's hard to debug

**What about restore?**
If re-adding RAG embeddings fails, you have a "published" document that **doesn't appear in AI search results**. In a clinical setting, that means doctors might not see critical guidelines.

**You need:** Idempotent operations with rollback, or a queue-based approach with retry logic.

---

### 4. The User Confirmation Flow is a UX Nightmare

Your flow:
Upload -> LLM Process -> RAG Search -> LLM Compare -> Block UI for User Confirmation

**Problems:**
1. **5-10 second blocking operation** - user thinks the app is broken
2. **What if user closes the tab?** - document is in limbo
3. **What if LLM is slow/down?** - no fallback
4. **Mobile users** - they won't wait for this

**Real-world scenario:** A clinician uploads a guideline during a busy shift. They don't have time to wait for your AI comparison. They close the tab. Now you have a half-processed document with no clear state.

## 🔴 Security Concerns Not Yet Addressed

### 1. Hash Collision Attacks Are Trivial

SHA256 has known collision scenarios. A malicious (or just unlucky) upload could:

```
File A: sepsis-guideline-v1.pdf (hash: abc123...)
File B: malicious-altered-sepsis.pdf (crafted to have hash: abc123...)
```

Your system would reject File B as a duplicate even though it contains different content. In a clinical setting, this could prevent critical updates from being uploaded.

**Mitigation:** Use **double hashing** (SHA256 + file size + first/last N bytes) or BLAKE3. Store multiple hash fields, not just one.

### 2. Frontend Hash Computation Is Tamperable

If you compute SHA256 on the frontend before upload:

```javascript
// Attacker intercepts and modifies
const fakeHash = 'e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855';
await saveDocument({ storageId, contentHash: fakeHash, ... });
```

The attacker bypasses duplicate detection entirely. **Never trust client-provided hashes.** Compute server-side in the mutation.

### 3. Archive/Restore Authorization Gaps

Who can archive? Who can restore? Your schema has `archivedBy` but no authorization checks. Consider:

- Can a regular user archive a guideline they didn't create?
- Can anyone restore an archived guideline?
- What's the audit trail for restore operations?

**Missing:** Role-based permissions for archive/restore actions.

## 🟠 Performance at Scale

### 1. RAG Search for Duplicates Will Kill Your Budget

Current RAG setup uses OpenAI `text-embedding-3-small` at $0.02/1M tokens. Let's do math:

```
Average guideline: 10,000 tokens
100 uploads/day × 10,000 tokens = 1M tokens/day = $0.02/day
Plus the comparison LLM call (Cerebras): ~$0.01 per comparison
Total: ~$3-5/day just for duplicate detection

At 1000 uploads/day: $30-50/day = $900-1500/month
```

**This is expensive for a feature that catches maybe 5% duplicates.**

Your proposed `by_contentHash` index will have hot spots:

```typescript
  .query("guidelines")
  .withIndex("by_contentHash", q => q.eq("contentHash", args.contentHash))
  .first();
```

With concurrent uploads, you get read contention. Convex handles this, but at high volume, you'll see latency spikes.

### 3. RAG Embedding Deletion Is Not Instant

When you archive a document:

```typescript
await rag.deleteByKey(ctx, { namespaceId, key: documentId });
```

This is **asynchronous** in the RAG component. Users searching immediately after archive may still see the document in results. You need to handle this gracefully in the UI.

```typescript
contentHash: v.optional(v.string()),

async function checkDuplicate(ctx, hash: string, size: number) {
  return await ctx.db
    .query("guidelines")
    .withIndex("by_contentHash", q => q.eq("contentHash", hash))
    .filter(q => q.eq("contentSize", size))
```

```typescript
export const indexDocument = action({
  args: { documentId, content, title },
  handler: async (ctx, args) => {
    // Compute hash BEFORE any LLM processing
    const crypto = await import('crypto');
    const hash = crypto.createHash('sha256').update(args.content).digest('hex');
    const size = new Blob([args.content]).size;

    const existing = await ctx.runQuery(internal.guidelines.checkDuplicate, { hash, size });
```
